## 背景与处置

整理重复协议不等于减少协调成本。重构应先删除无效步骤和无人消费的记录，再判断剩余内容是否需要共享。专业判断仍需要依据；真实反馈和可复核成果比“走完流程”更重要，Skill 组合本身不保证可靠性。

已撤回以全量判据标签、统一验证调度字段和协议检查器为主线的旧方案，并移除其未实施计划及过时评估正文。不要恢复这些预设交付物；确有独立需求时重新论证。已提交的原始评估留在 Git 历史，不再作为当前设计依据。

## 范围与顺序

基线包含 24 个已完成 Skills、11 个 workflow。预计 7–9 个 Skill 有实质调整，连同引用、README、AGENTS 和必要校验，约涉及 20–35 个文件；不是重写全部 Skills，也不预先决定新增脚本或删除入口。

1. **先确认试点契约**：决定调用模式、输入充分性、产出和真实停止条件，再重订实施计划。
2. **试点修复/实现路径**：`systematic-debugging`、`tdd`、`verification`、`code-review`、`fix`。
3. **验证后推广**：处理 `grilling`、`spec`、`plan` 的需求/规划路径。外部发布和专门交付入口单独评估。

不新增工作流引擎、Pi 扩展或安装发布机制。现有显式授权在对应契约获确认并完成迁移前继续有效。

## 试点验收

覆盖原因已知的小缺陷、原因未知的故障、普通功能、文档/配置修改、缺测试环境、修改后证据过期。

用相同任务、模型和环境对比现有 Skills 与自然组合版本；条件允许时增加不加载相关 Skills 的对照。保留实际调用、工具结果和用户干预记录，比较：

- 行为正确性及完成声明的证据；
- 必需检查或授权边界是否遗漏；
- 过度处理、重复调查、重复验证和循环调用；
- 用户纠正次数、执行步骤、上下文与时间成本。

有限样本只支持已观察范围的结论。试点无改善时调整或撤回候选改动，不以文本变短、静态校验通过或迁移完成率代替行为验收。

## 工程量粗估

按一名熟悉仓库的维护者加 agent 辅助估算；不包含运行机制开发、全局配置改造或外部操作费用。

| 工作项 | 预计投入 |
|---|---:|
| 确认职责与授权边界，补足参考调研 | 0.5–1 天 |
| 重构核心 Skills | 1–2 天 |
| 清理引用、字段和交接说明 | 0.5–1 天 |
| 更新入口文档与必要结构校验 | 0.5 天 |
| 任务对照验证与修正 | 1–2 天 |
| 收尾、镜像核对和变更记录 | 0.5 天 |
| **合计** | **4–7 个工作日** |

试点约 1–2 个工作日，包含在合计内；完成后再经过 1–2 周实际任务观察，不要求全职投入。最大不确定性是调用边界和组合歧义，不是文档字数。此处不是排期承诺。

## 未决项

- `spec`、`code-review` 等的最终调用模式。
- `fix` 保留为薄入口还是方法型 Skill，以及哪些停止/交接条件有独立价值。
- 哪些制品格式确有消费者，哪些输入可直接来自对话或已有证据。
- 对照任务、模型/环境、记录方式和必要成本授权。
