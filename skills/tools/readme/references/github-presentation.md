# GitHub presentation

Load this reference for profile READMEs or when the user explicitly asks for repository About text, topics, badges, discoverability, or an Awesome-style list. Keep README authoring grounded in repository evidence; verify current GitHub limits and UI behavior against official GitHub documentation before quoting them.

## Repository landing page

Align these surfaces around the same project identity:

| Surface | Job |
|---|---|
| Repository name | Memorable identifier |
| About description | Plain-language purpose and audience |
| Website | One canonical product or documentation destination |
| Topics | Specific technology, purpose, and category labels |
| README opening | Expanded answer: what it does, for whom, and why it matters |

Recommend metadata separately from file edits because About, Website, and topics are repository settings. Avoid keyword lists and unsupported ranking promises; clarity and consistency are the target.

## Badges and media

Use a badge only when its live value helps a reader decide, such as build status, package version, documentation, or license. Prefer first-party status sources. Group a small badge set after the title or opening statement.

For images:

- use stable repository-owned assets when practical;
- provide meaningful alt text;
- verify light and dark theme legibility;
- keep critical setup information available as text;
- label third-party widgets as optional and tolerate their failure.

## Profile README

A profile README is an identity and navigation page, not a product manual.

Use a short sequence:

1. name or organization and current focus;
2. selected work with one outcome-oriented sentence per item;
3. canonical links or contact methods, each listed once;
4. optional compact activity proof.

Check that pinned repositories and profile metadata support the same story. Keep detailed setup, feature, and contribution material in each project repository.

## Curated lists

For an Awesome-style list:

- define the topic boundary and acceptance bar before the entries;
- organize for lookup rather than chronology;
- annotate why each item belongs;
- provide contribution and review rules;
- check links and remove abandoned entries when the maintenance policy requires it;
- follow the upstream Awesome conventions when seeking inclusion in that ecosystem.

## Claims requiring current verification

Consult official GitHub documentation before stating:

- character or topic limits;
- supported Markdown, alert, image, or profile behavior;
- GitHub Pages URLs, build sources, quotas, or deployment behavior;
- search, Trending, recommendation, or indexing behavior.

Describe observed outcomes rather than presenting speculative SEO or AI-citation formulas as facts.
