# Workflows — 16 件阶段方法 Skill：设计思路与用法

这个目录（`skills/workflows/`）是一套给 Pi coding agent 用的"工程方法"Skill。思路很简单：把工程工作切成一个个阶段——澄清想法、写规格、做计划、修 Bug、写测试、验证、评审——每件 Skill 负责一个阶段，教 agent 这个阶段怎么做才算规范。

读完本文你会明白三件事：这套东西为什么这么设计、各阶段怎么自然拼接、16 件各自在什么时候用。每件 Skill 的完整规则以它自己的 `SKILL.md` 为准；安装方法和常见场景的组合表在[仓库根 README](../../README.md)。

## 设计思路

### 一个阶段，一件 Skill

工程任务很少恰好走完全程：多数时候你只想要其中一步。所以每件 Skill 只负责一个阶段——做什么、按什么顺序、做完留下什么证据——而不是给你一套"必须从头走到尾"的大流程。

这样拆还有一层用意：**阶段之间的结论不能串门**。诊断的 Skill 到"根因被证明"就停，不顺手把修复也做了；TDD 只留下行为测试的证据，不替验证阶段宣布"整体没问题"；验证只报告门禁事实，不冒充评审或发布批准。每段做好每段的事，结论才可靠。

### 结论靠证据，不靠"装了哪件 Skill"

- 说"做完了"，标准只有一个：命令跑过、输出和文件状态对得上。**旧结果不算数**——代码又改过，就得重跑。
- 某件 Skill 没安装？agent 按同一方法自己做，不许因为"缺 Skill"跳过检查或虚报通过。
- `BLOCKED` 只表示真的被卡住：缺证据、缺授权、环境不可用。**"没装那件 Skill"不是 BLOCKED 的理由。**
- 验证状态（`READY` / `NOT READY` / `BLOCKED`）全局只有一套合成规则，由 `verification` 定义、`code-review` 遵守同一套：当前该跑的必要检查没跑成 → `BLOCKED`，有检查失败 → `NOT READY`，全部通过才 `READY`。不存在"跑了一部分所以算半个 READY"。

### 拆得越细，安全线越不能松

去耦（可以单独装、可以缺着用）不降低行为红线：

- 有副作用的操作，动手前先问用户；
- "验证通过" ≠ "评审通过" ≠ "可以发布"，各自是独立的结论；
- 原型代码永远不进生产；评审的结论和验证的状态是两件分开记录的事；
- 少数会对外部世界产生影响的 Skill（`publish-tickets` 发票、`session-handoff` 写交接）只能由用户点名调用，agent 不能自作主张。

### 门面写清主干，细节放 references

每件 `SKILL.md` 读一遍就够你判断"何时用、怎么走、以什么收尾"；分支情况和细则是放进旁边 `references/` 目录的，需要才翻。跨 Skill 共用的格式只保留一份原件：交接文档的格式只由 `living-docs-governance` 持有，`session-handoff` 只是负责把它写出来——所以点名安装 `session-handoff` 时会自动带上 `living-docs-governance`。

## 组合方式：按需拼接，没有总管道

这套 Skill **不预设组合**：没有一件"总指挥"Skill 来决定流程，也没有"必须整套安装"的要求。组合发生在 agent 调用时——

- 方法型 Skill（除注明外全部 14 件）：Pi 见到合适的任务会自己选，你也可以用 `/skill:名字` 点名调用；
- 事件型入口（`publish-tickets`、`session-handoff`）：只能你点名。

**上一阶段的产物，是下一阶段的可选输入**：grilling 留下决策集，spec 留下带编号的需求/验收条件，plan 留下切成片、标好基线的计划，TDD 留下红绿测试记录，验证与评审各自落一份报告。这些产物——

> 还在保质期就接着用；过期或没有，就直接从仓库现做。

所以没有"非交不可的作业"：一个原因明确的 Bug，不必先走拷问和写规格，从诊断开始就行。"保质期"看产物声明的范围、顺序和代码状态是否还对得上；对不上就重跑，不能因为有份旧报告就免检。

每次拼接，agent 都要回答三个问题：

1. **根因已知吗？** 没证明原因前不许直接改行为——先诊断。
2. **改行为还是改需求？** 代码行为其实符合你的意图、你却想改——那是新需求，走 spec/plan，别让 fix 硬接。
3. **要证明什么？** 实现完跑 `verification` 拿新鲜门禁；想要独立结论跑 `code-review`。

常见场景（新功能、修 Bug、迁移、评审……）分别怎么拼，见根 README 的[真实场景组合表](../../README.md#真实场景组合)，这里不重复维护。

## 16 件 Skill 简介

按使用时机分五组。多数是"一个阶段的方法"；`codebase-design` 是词典、`resilience` 是规则集，这两件不属于某个阶段、几个阶段都可能用到，说明里写清楚了。

### 澄清与写契约

- **[grilling](grilling/) — 动手前先把想法拷问一遍。** 对计划、设计、点子一轮轮追问边界问题，直到真正想清楚，只留下"决策集"（含否决了哪些、还有哪些没想明白），不写规格。适合在写 spec 或 plan 之前。
- **[domain-modeling](domain-modeling/) — 统一说法，留住理由。** 把项目里反复出现的术语收进 `CONTEXT.md` 词汇表，让大家说同一套词；只有"很难反悔、不看上下文就费解、而且真有取舍"的决定才写 ADR。防止每个新会话都重新发明词汇和理由。
- **[spec](spec/) — 把商量好的事写成行为规格。** 产出与实现无关、可以验收的契约：需求（REQ）、不变量（INV）、验收条件（AC）分开编号，实现和验收都对着它做。行为契约缺失、或要"按这份规格实现"时用。

### 规划与设计

- **[plan](plan/) — 基于仓库现状的实现计划。** 对照当前代码、门禁和基线版本，把契约拆成改哪些文件、分几步做、每步怎么验证，落成一份计划文件。按风险选深度（精简 / 标准 / 大型），每项验证都写清证明什么、谁负责、哪个阶段到期，下游不许另行解释。
- **[codebase-design](codebase-design/) — 设计词典。** 提供 module、seam、depth、leverage 这些设计词汇和"还能不能更深一层"的判据，规划怎么切分、测试接口选在哪、设计怎么评审时，大家用同一套词。它没有流程，只是一本词表加判据。
- **[prototype](prototype/) — 抛弃式原型。** 用一个临时原型回答**一个**设计问题（这状态机撑得住吗？UI 这样排顺手吗？），然后只交证据：答案、原型在哪、看到了什么、局限是什么。原型代码永不进生产——真要实现，走 plan + TDD 在正经代码里重做。
- **[resilience](resilience/) — 比较特别的一件：它给的不是流程，是"这类改动必须满足什么"。** 凡是失败会跨到远端依赖、消息队列、共享容量边界的改动——涉及超时、取消、重试、幂等、过载、恢复——都要按它的规则检查：等待和重试必须有上界；重试只有幂等或对账兜底才安全，而且一条调用路径只能有一个重试负责人；超时没等到结果、副作用可能已经发生的，一律当"结果未知"处理，直到幂等记录或对账给出答案；过载要显式拒绝或降级；半途失败时每个中间状态都要有人负责善后。它带你一步步对照检查，最后给一份评估（`COMPLETE` / `BLOCKED` / `OUT OF SCOPE`），**不下"实现完成"的结论**：设计阶段它把要证明的失败场景交给 plan，评审已有实现时把验证要求交给 verification。

### 执行与修复

- **[publish-tickets](publish-tickets/) — 把批准的计划发布成票（只能你点名）。** 按计划里切好的片，一片一张票，保留依赖关系、需求追溯和基线版本号；不重新切分、不擅自改图。跨多个会话分片执行时用。
- **[systematic-debugging](systematic-debugging/) — 先证明原因，再谈修复。** 对原因不明的失败（Bug、回归、偶发测试、性能问题、构建失败）做最小复现和可证伪实验，证明根因和它违反的规则，然后**停在修复之前**、交接诊断。TDD 红灯红在错误原因上、或者眼看要开始瞎试时，都先回到这里。
- **[fix](fix/) — 端到端修一个问题。** 复现失败 → 证明原因 → 做最小修改 → 跑终局验证。覆盖 Bug、构建/CI 失败和评审确认过的问题；原因已经查明的修复也可以直接从修改这一步开始。
- **[tdd](tdd/) — 测试先行的行为开发。** 沿着一个垂直切片走"红 → 绿 → 重构"：先在真实测试接口上写一个会失败的测试（红灯必须真红，作为历史证据），再实现到它通过（绿灯），最后在**所有修改完成后**重新采集门禁和状态作为成稿证据。行为先于实现；做新功能、或原因已明确的修复时用。
- **[coding-standards](coding-standards/) — 与语言无关的代码质量基线。** 按仓库自己的规则检查命名、可读性、控制流、重复、错误处理等。verification 不可用时就按同样方法自己跑门禁，"未验证（UNVERIFIED）"只许用于真没法取证或纯属观察的条目。窄改动、实现和评审的代码质量面归它；架构、安全、韧性、测试流程归更专门的 Skill。

### 验证与评审

- **[verification](verification/) — 用新鲜证据给改动下状态。** 跑齐该跑的门禁（类型、lint、测试、构建、生成物一致性、验收），按统一规则给结论：该跑的都过了 → `READY`；有必过的失败了 → `NOT READY`；必过的检查跑不成 → `BLOCKED`；属于后一阶段的证据标 `PENDING`，不挡这一阶段。声称成功、准备评审或发布之前，先跑它。
- **[code-review](code-review/) — 请一双没写过这段代码的眼睛。** 只读地评审 diff：先弄清当前验证状态（复用对得上号的验证报告，或自己跑窄门禁，合成规则与 verification 相同），再按四个视角找问题、给每条发现分级，最后给出评审结论（`APPROVE` / `APPROVE WITH COMMENTS` / `REQUEST CHANGES`）。报告落盘，不改被审代码。想要独立结论而不是自己说自己好时用。

### 治理与交接

- **[living-docs-governance](living-docs-governance/) — 让长期文档不腐烂。** 给项目里长期存在的文档分派角色（Constitution / Map / Status / History）和新鲜度规则，并负责把它们接进 agent 的启动指引。文档和代码脱节、会话间丢上下文、删掉的东西反复复活时用。交接文档的格式也归它持有。
- **[session-handoff](session-handoff/) — 把当前会话压缩成交接（只能你点名）。** 在你要求时，把会话压成一份放在仓库里（默认 `docs/handoffs/current.md`）的导航式交接：当前状态、关键产物路径、下一会话怎么开场。只记路径与修订、不复制内容，写完后重新采样仓库状态。格式由 `living-docs-governance` 提供。

## 阅读与维护

- **每件 Skill 自己的 `SKILL.md` 才是准绳**：本文是导航，完整流程、边界和例外以它为准。
- **根 README 是总览**：安装方法、调用列图例、场景组合表以根 README 为准；跨 family 的设计原则、分层与依赖方向以 [DESIGN.md](../../DESIGN.md) 为准；各文档改动时保持一致。
- **有自动校验**：新增或改动后跑 `bash scripts/validate.sh`（检查 frontmatter、引用可达性、根 README 清单与调用契约），全绿才算过。
- **新增成员**：先在 `processing/skills/` 起草验证，再移入本目录；同时更新本文的分组与简介、根 README 的目录表。
